# 2026-08-28

## 瀏覽器主控台 pyodide 錯誤再次出現（GPU info check failed: get / borrowed proxy destroyed）
跟 [2026-08-27.md](2026-08-27.md) 最後一條是同一組錯誤訊息。追查後確認：

- `index.html` 實際載入的是 `web/frontend/src/components/action.py`（`<script type="py" src="action.py">`），
  不是 `python.py`——後者是專案裡另一份未被任何頁面引用的重複草稿檔（新增、未追蹤）。
- `action.py` 目前原始碼裡這兩個問題都已經有對應修正：
  - `api_get()`/`api_post()`（195-216 行）已經用 `.to_py()` 把 `resp.json()`
    回傳的 JsProxy 轉成真正的 Python dict，`check_gpu()` 裡 `data.get(...)`
    才不會因為 JsProxy 沒有 `.get()` 而丟 `AttributeError: get`。
  - `capture_and_send()`（598-601 行）的 `toBlob` resolve 已經用
    `create_once_callable()` 包住，避免 borrowed proxy 在非同步回呼觸發前
    就被銷毀。
  - 所有 `addEventListener` 也都已經用 `create_proxy()` 包住 handler。
- 後端 `web/backend/app.py` 的 `public_file()`／`index()` 已經對 `action.py`
  等靜態檔案回應加上 `Cache-Control: no-cache`（136-150 行），理論上瀏覽器
  每次都要跟後端確認檔案有沒有變過，不應該直接吃舊快取。

結論：程式碼本身沒有退回舊版，錯誤重現最可能的原因跟昨天懷疑的一樣——
瀏覽器分頁仍在用修正前的 action.py（`no-cache` 只保證「必須重新驗證」，
不保證瀏覽器一定會發出驗證請求；PyScript/Pyodide 本身對抓到的 .py 原始碼
也可能有自己的一層快取，不一定完全遵守標準 HTTP 快取語意）。

**待使用者確認**：開 DevTools → Application → Clear storage（或至少
Ctrl+Shift+R 硬重新整理）後重新載入頁面，錯誤是否還會出現。如果清乾淨
快取後仍然出現，才需要回頭懷疑程式碼本身。

（附帶：修 bug 過程中誤把同名但未被使用的 `python.py` 也補上同一個
`.to_py()` 修正，該檔案不影響目前實際執行的網頁，純粹是讓兩份重複檔案
的內容保持一致。）

## 追加：「borrowed proxy destroyed」真正根因找到了，不是快取問題

用 Playwright（假攝影機裝置）實際跑一輪「開啟相機」流程後，主控台穩定
重現 4 次同一則錯誤，時間點剛好對到 `DETECT_INTERVAL_MS = 500`ms 的偵測
輪詢間隔——鎖定是 `start_camera()` 裡這一段（原本行號約 541-543）：

```python
_state["loop_handle"] = window.setInterval(
    lambda: asyncio.ensure_future(capture_and_send()), DETECT_INTERVAL_MS
)
```

`api_get()`/`capture_and_send()` 的 `toBlob` 回呼、所有 `addEventListener`
都已經用 `create_proxy()`/`create_once_callable()` 包過，唯獨這裡傳給
`window.setInterval()` 的 lambda 是裸的 Python callable。pyodide 只有在
「呼叫當下同步結束前」保證這種借用代理（borrowed proxy）有效——
`setInterval()` 這一行呼叫本身一返回就把它銷毀了，之後每 500ms 計時器
真正觸發、JS 端呼叫它時就會撞上
`This borrowed proxy was automatically destroyed at the end of a
function call`。實際影響不只是主控台洗錯誤訊息：`capture_and_send()`
從此再也沒有真的被呼叫過，物件偵測畫面會卡在「偵測中…」，永遠不會有
偵測結果——這解釋了 2026-08-27 跟今天稍早那則「懷疑是瀏覽器快取舊版
action.py」的誤判：當時看到的其實是同一個一直沒修好的 bug，不是快取。

**修正**：把該 lambda 也包進 `create_proxy()`（跟檔案裡其他 JS callback
同一套寫法），已套用在目前的 `action.py`。修完後用 Playwright 重跑同一輪
操作，主控台不再出現這則錯誤。

## 追加：物件偵測 WebSocket 第一幀後端會斷線（待查，非本次改動範圍）

修完上面那個 bug 後用 Playwright 假攝影機重測，`/ws/detect` 連線正常
`accept()`、瀏覽器端也正常送出第一幀（`WS SENT` 有觸發），但後端從頭到尾
沒有送回任何一則 `WS RECV`，連線隨即被伺服器關閉（`WS CLOSE`，無法從
瀏覽器端看到明確關閉代碼/原因）。對照 `web/backend/app.py` 的
`detect_stream()`：

```python
while True:
    data = await ws.receive_bytes()
    ...
    await ws.send_json({"detections": detect(image, conf=conf), ...})
```

`detect()`（`detector.py`）拋例外不會被 `except WebSocketDisconnect`
接住，最可能是收到第一幀後 `detect()` 內部丟例外，FastAPI/uvicorn 把
連線直接關掉。目前手上的測試環境（合成假攝影機畫面）無法排除是不是
單純因為假畫面觸發了 YOLO 模型某個邊界情況；有沒有在真實鏡頭畫面下
也會斷線，需要使用者實機操作才能確認。這次改動沒有動到
`web/backend/app.py`/`detector.py`，記錄下來留給下一輪排查。
