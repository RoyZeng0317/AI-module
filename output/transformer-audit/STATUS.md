# Transformer 現況檢查

檢查日期：2026-10-25。使用者主要問題為「不記得上下文或不遵守要求」。本次僅讀取程式、資料與權重，進行本地推論；沒有重訓、切換權重或使用外部模型／API。

## 目前實際使用的架構

| 項目 | 現況 |
|---|---|
| 程式 | `tranning/transformer_chat.py`，自行建立的decoder-only Transformer |
| 一般聊天權重 | `tranning/gpt_chat_runs/model.pt` |
| 參數量 | 17,465,088，實際載入後統計 |
| Transformer層／注意力頭／隱藏維度 | 8／6／384 |
| BPE詞彙數 | 8,000 |
| 上下文窗口 | 512 tokens，不是512字，也不代表已接入對話歷史 |
| 預設生成 | 最多60個新tokens；temperature=.7、top_k=30、top_p=.85、repetition_penalty=1.3 |
| 目前問答資料檔 | `data/pairs.json`，742筆，均為prompt/reply欄位；不能由此推斷現行權重訓練時用了全部742筆 |
| 現有中文語料檔 | `data/corpus_zh_starter.txt`，4,588,307字元；config沒有記錄本權重當時實際使用哪份語料 |

一般聊天路由在 `tranning/chats.py`；程式碼分支仍是另一套模型。已審核句型可能先由 `chat_quality.dialogue_reply()` 精確比對回答，非模型生成；生成後的結構檢查也可能改成澄清訊息。前端畫面回覆不等於每次都直接顯示Transformer原始輸出。

## 已確認的問題

### 1. 本地Transformer沒有收到對話歷史

桌面 `Conversation` 保存 `self.history`，也傳給 `smart_reply_traced(history=...)`。但一般分支呼叫的是 `transformer_chat.reply(message)`，沒有傳history；`reply()`簽名也沒有history引數，實際只編碼 `message + SEP`。歷史目前只在明確選用的NVIDIA分支轉交；本次沒有呼叫該分支。

因此「記得剛才使用者叫什麼、它指哪個物品、上一輪要求用什麼格式」在這條本地路徑沒有足夠輸入支持。介面存了聊天紀錄、磁碟有session，和模型每次推論能讀到它們，是兩件不同的事。

### 2. 訓練格式是單輪問答，不是多輪角色對話

`ChatSFTDataset`建立 `prompt + SEP + reply + EOS`，只對回答計算損失。它沒有統一建立system/user/assistant多輪結構；即使在推論時直接拼上一大串歷史，也不能保證既有模型理解角色與指令優先順序。此為訓練格式與使用需求的差距，不是單純調temperature可解決。

### 3. 存下memory不等於自動餵給Transformer

本地一般聊天與 `reply()` 沒有讀取 `memory_store` 的路徑，沒有把持久記憶組成模型上下文。斜線指令提示詞即使作為message傳入，對模型仍是一般文字，不等於有訓練過的system角色或可靠約束。

### 4. 現行模型對明確指令與語意仍不可靠

固定seed=42、CUDA、目前正式權重、預設取樣設定，直接呼叫原始 `reply()`：

| 輸入 | 實際原始輸出 |
|---|---|
| 我叫小明，請記住我的名字。 | 好，謝謝你提醒，你也要說過去看， |
| 我叫什麼名字？ | 我叫 sinco |
| 請只回答一個中文字：好 | 好的,我盡量都用中文回覆 |
| 請用繁體中文，分成兩點說明什麼是機器學習。 | 我也是的名字，別把文字切成模型給自己、最適合、最好的文字,如I'ly inco |

完整6筆樣本與參數量在 [raw_samples.json](raw_samples.json)。這是有界抽樣，不能換算整體準確率；第一、二句分別呼叫不會保留模型對話狀態，正好對應本地reply介面的限制。

這些輸出在目前 `chat_quality.output_issue()` 檢查中均未被標記，顯示結構／少數關鍵字檢查不能驗證一般語意正確性與格式遵守。

### 5. 訓練與驗證有明顯落差

主用 `gpt_chat_runs/history.json` 共41epochs，最低val_loss在epoch26：train=.5157、val=2.1294；最後epoch41：train=.2465、val=2.1556。訓練繼續變好，但驗證不再改善，支持過擬合風險。

`_run_epochs()`最後會恢復最低val_loss的best_state，所以不能將「最後一列loss」說成當前權重必定對應的loss。`gpt_chat_runs` config沒有 `finetune_regularization` 記錄，不能證明後來新增的凍結／label smoothing／語料混訓已用於正式權重。v2/v3目錄存在，但一般分支沒有指向它們；不同tokenizer／資料切分的loss不能直接當成公平排名。

## 建議的加強順序

1. 先修對話上下文組裝：共用路由把有限歷史交給本地Transformer，設定角色分隔、輸入預算、舊輪裁切及跨聊天隔離；保留本輪問題，不讓長歷史吃光512tokens。
2. 配套建立多輪訓練與評測：姓名／物品指代、延續前輪格式、修改前輪要求、否定與衝突指令；訓練與測試按整段對話分開，不能把相鄰輪拆入兩組。
3. 再處理指令微調與過擬合：以新目錄驗證凍結部分層、適當學習率與語料混訓，保留現行模型作基準。不能照搬YOLO配方、僅增加epochs或放大模型，也不使用YOLO的預訓練例外載入外部語言模型。
4. 明確區分「保存在聊天紀錄」「送入推論上下文」「寫入長期memory」「模型訓練學會」四個機制；先決定哪些記憶相關且允許送入，不整份無限制拼接。
5. 驗收分兩層：程式測試確認歷史有送入、裁切與隔離正確；真模型測試確認回答真的使用前文與遵守格式。測試通過串接不等於模型理解已通過。
